Xây dựng hai đường nạp inbound vào queue — webhook (primary, low-latency) và reconciliation poller (backup) — slice thoả criterion #1 (inbound đến queued worker qua webhook + poller, xử lý exactly once). Cả hai feed cùng queue của plan 03; dedup tự động vì cùng idempotency key (D-02/D-09).

Mục đích: Hiện thực D-09 (webhook primary + reconciliation poller) với bảo mật webhook (HMAC-SHA256 custom secret header — Freshdesk không có HMAC native, RESEARCH A3) chống spoofing. **Design: RESOLVE-THEN-ENQUEUE (D-02).** Cả webhook receiver và poller đều gọi `GET /api/v2/tickets/{id}/conversations`, chọn latest inbound customer message (dùng `should_suppress` từ 02-04 làm single source of truth — fix #4, KHÔNG inline điều kiện riêng), tính key `ticket_id:inbound_msg_id` thật, rồi enqueue. **Poller window DURABLE qua queue.poller_checkpoint (fix #3)** — restart không mất window. KHÔNG dùng sentinel `inbound_msg_id=0` và KHÔNG để worker re-key.

MODULE: queue helpers ở `src/work_queue/` (fix #10). SQL tham chiếu schema `queue`.

Output: signature.verify, FastAPI receiver (verify → resolve → enqueue), shared `resolve_inbound_and_enqueue` helper (dùng should_suppress), poller reconcile_once + durable checkpoint + loop cadence.

DATA CONTRACT — Resolve-then-enqueue (D-02, dùng IDENTICAL ở cả webhook + poller):
  resolve_latest_inbound_msg_id(client, ticket_id, selless_sync_user_ids) -> int | None:
    1. convs = await client.get_conversations(ticket_id)
    2. chọn latest conversation; gọi should_suppress(conv, ...) (single source of truth — fix #4) để quyết định "real inbound customer message". Nếu suppress (non-customer/auto/sync) → return None → KHÔNG enqueue.
    3. return conv.id của latest inbound (đây LÀ inbound_msg_id trong key).
  → key = compute_idempotency_key(ticket_id, inbound_msg_id) — webhook và poller tính RA CÙNG key từ CÙNG ticket state.
  → enqueue_ticket(conn, ticket_id, inbound_msg_id, payload); UNIQUE index trên idempotency_key → ON CONFLICT DO NOTHING là dedup guard duy nhất (không read-then-write race).

Webhook (RESEARCH § FastAPI Webhook Receiver):
  - Freshdesk KHÔNG có HMAC native (A3) → shared secret HMAC-SHA256 header X-Freshdesk-Signature; verify bằng hmac.compare_digest (constant-time) TRƯỚC mọi I/O.
  - payload chỉ cần ticket_id; webhook KHÔNG chứa conversation body (Pitfall 1) → resolve step fetch conversations (bắt buộc dù sao).
Poller (RESEARCH § Poller fallback D-09):
  client.list_updated_tickets(since) → mỗi ticket chạy CÙNG resolve_latest_inbound_msg_id → enqueue → ON CONFLICT auto-dedup với webhook path. last_since persist vào queue.poller_checkpoint.
